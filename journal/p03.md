# P03: one conductor, three spellings, one vendor

The lab is [Cat-M MQTT node with GNSS stamp](../chapters/03-cat-m-mqtt-node-with-gnss-stamp.md).
Its record is mostly about a documentation hazard rather than an error, and it is
the reason a convention in this volume that looks like padding is not.

## The reading, Saturday 3 October 2026

This board was read after P02's withdrawal, to find out whether it made the same
claim. It does not. The SIM7070G leaves the draft's indicator pin alone, and
puts the module's power key on header pin 7, BCM GPIO4, exactly where the
SIM7020E puts it.

Two other things it does claim are worth knowing before wiring:

| Connection | Header pin | BCM | Condition |
|---|---|---|---|
| DTR | 37 | GPIO26 | **Only** with the DTR jumper in position A. Default is disconnected |
| IO level select | jumper | | Default 3.3 V. The other position makes the HAT's logic **5 V** |

That second row is the single connection the volume's electrical safety lab
exists to prevent, offered on this board as a two-position jumper. Never move it.

## The near miss

An intermediate version of the indicator correction had used BCM26. That is the
pin the DTR jumper connects in position A, and it is also a board-address pin on
the data acquisition HAT in another lab.

**It was abandoned for the second reason, found while writing a different
chapter, before anyone had read this board's pages properly.** The right answer
arrived partly by luck. The reading is what settles it now, and the luck is
recorded because a volume that only prints its successful reasoning teaches
readers to trust reasoning that happened to work.

## The part that generalises: one pin, three spellings

The module's own hardware design document settles only half the question. It
confirms which lines the module has to route, PWRKEY on module pin 1, DTR on 3,
RI on 4, DCD on 5, CTS on 7, RTS on 8, STATUS on 66 and NETLIGHT on 52.

**Which Raspberry Pi header pin each of those reaches is the carrier board's
decision, not the module's.** A module datasheet cannot answer it and the HAT's
own pages must. That distinction is worth internalising before reading any
vendor material: a module document and a carrier document answer different
questions, and confusing them produces claims that are individually sourced and
jointly wrong.

Then the spellings. The vendor's product page calls the power key pin "P4". The
same vendor's wiki calls it "P7 (wiringPi number)". Neither page says which
numbering scheme it is using. **They are the same conductor:** wiringPi 7 is BCM
GPIO4 is physical header pin 7.

A reader who assumes physical numbering on the first page wires the power key to
the 5 V rail.

This is why every pin in this volume is given as header pin and BCM number
together, in every table, every time. It reads as padding until the first time it
is not.
