# P18: a chapter that had drifted away from the repository, and a library that waited for its second user

The lab is [Nucleo USB-CDC recorder](../chapters/18-nucleo-usb-cdc-recorder.md),
written on **Friday 16 October 2026**. Nothing in it has touched a Nucleo. What
follows is how the host half came to be written before the board, what was
found on the way, and one thing that is still only a claim.

## What started it was not this lab

P04's host side became a C program at the start of October. The chapter was not
changed with it. For two weeks the published chapter told a reader to install
three Python packages and write `p04_fft.py`, while the repository shipped six
subcommands in C that did all of it, and nothing in twenty chapters named the
directory they were in.

That is worth stating plainly because of who it hurts. A reader types from the
chapter. The chapter was the published version of that lab, and the program
beside it was a thing they had no route to. Every check in the repository was
green throughout, because no check compares a chapter with the code it talks
about, and no check could: the chapter's code blocks are prose, deliberately,
so that what a reader types is the thing they read rather than a file that may
have moved on.

Fixing that is what made P18 the next lab rather than one of the four others
that could have been. A second program was going to be written either way; a
second program whose chapter already agreed with it was the cheaper place to
start.

## The lift that was promised, and what it turned out to hide

When P04 was written, the note in its README said the shared half would move
into a library beside it once a second lab needed one, rather than being
guessed at in advance. P18 needs exactly one thing P04 already had: the
accounting of gaps, duplicates and reorders over sequence numbers.

The lift was not a copy. P04's version compared sequence numbers with a plain
less than:

```c
if (seq < t->last_seq) {
    t->reorders++;
    return;
}
```

That reads the wrap of a 32-bit counter as a jump backwards of four billion. At
one kilohertz a counter reaches its maximum after about four and a half weeks,
so no capture P04 will ever take can reach it: the blocks are 2048 samples each
and the longest run in the volume is seconds. P18 is the lab whose chapter
explicitly contemplates a sink that runs for a week, and its own pitfall list
already said the comparison needed writing for that case.

So `lib/seqtrack.h` holds unsigned serial arithmetic instead, the distance taken
modulo the range with half the range as the dividing line, and both labs use it.
P04 keeps the name `p04_transport` as a typedef, because the chapter, the suite
and six call sites use that name and renaming them would change what a reader
sees without changing anything they can observe.

**The defect was latent, not live.** No published number of this volume was ever
wrong because of it. It is recorded here because a latent defect found while
moving code is the ordinary way such things are found, and because the lift
would have been worth doing even if it had been a straight copy.

## One property of the accounting that surprised the suite

A sample that arrives after its successor is counted twice over: once as a gap,
at the moment the successor arrived and the earlier number had not, and once as
a reorder when it turns up. The gap is not taken back.

That was not a decision at first. It was found by writing a synthetic stream
with one swapped pair in it, predicting one reorder and no gaps, and getting one
reorder and one gap. The arithmetic was right and the prediction was wrong.

Taking the gap back would need a window of sequence numbers held open, and a
window needs a policy for how long to hold it, which is a larger decision than
either lab needs. A USB CDC pipe and a recorded file both deliver in order, so a
reorder means something unusual happened, and two numbers describing it are more
useful than one number quietly adjusted. It is now written down in the header
rather than being rediscovered by the next person who predicts a zero.

## The two faults this lab exists to keep apart

The chapter already said it in one sentence: a rate that sits well under 1 kHz
with no dropped samples at all is a different fault from a gap. The program is
built around that sentence. `verify` prints three lines, for loss, rate and
integrity, and prints all three even when they pass, because at the bench a slow
stream and a holed stream feel the same.

The third line is the one that was not in the chapter. A capture that cost the
recorder a thrown-away line is not a capture of the stream, whatever its loss
figure says, so an over-long or unparsable line fails the acceptance test
separately from either number.

Two other refusals came out of the same thinking:

**A rate is not claimed unless it was measured.** Reading a capture file takes
milliseconds, and samples divided by that describes the disk. The report carries
a flag for whether the source was running in real time, and `verify` refuses an
unmeasured rate unless told in as many words to allow it. The workflow checks
both halves of that: the clean capture passes with the flag and fails without
it.

**An over-long line is refused whole.** The obvious reader hands back the part
that fitted and then the remainder, and the remainder begins with digits, so it
arrives as a sample nobody sent. The symptom would be a loss figure that
improves as the stream gets worse. The suite writes a line of 638 characters
into a 512 character buffer and checks that the two good lines either side of it
are still 1 and 9, and that nothing else appeared.

## What was only a claim, and what the first compile said

Written above before any of it had been compiled: the authoring laptop has no
compiler it may use, so the first build was the push, and a red one was the
expected way to find out what the compiler had to say.

**It was not red.** Built later the same day, Friday 16 October 2026, under
`-Wall -Wextra -Werror -Wshadow -Wpointer-arith -Wstrict-prototypes
-Wmissing-prototypes`: no diagnostics, and 94 checks with none failed. The
stricter pass, which adds `-Wconversion`, `-Wsign-conversion` and
`-Wdouble-promotion`, was clean as well.

That last part is worth one sentence of caution rather than satisfaction. P04's
strict pass failed on every run for three runs and the failure was invisible
because of how a `continue-on-error` step is reported, which is what
[p04.md](p04.md) is about. P18's strict pass passing on the first attempt is a
better outcome but it is the same kind of evidence, read from a step that is
still allowed to fail quietly. The reason it came out clean is not luck: every
conversion in this program is written out, the one place a count becomes a
number is `p18_loss_percent`, and timing is `double` throughout rather than
`float` promoted at the point of use. Which is a hypothesis about why, and the
next program will test it.

Nothing here has been near a Nucleo. Unlike P04, though, there is no
missing piece waiting for one: a character device is one more source, `stty`
sets the line discipline before the program opens it, and the command in the
chapter differs from the command in the suite by the value of one argument.
That is a claim too, and it is the first thing the board will test.
