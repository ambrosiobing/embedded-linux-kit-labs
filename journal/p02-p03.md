# P02 and P03: two labs written together, and the first shared file that was not a rescue

The labs are [NB-IoT PSM/eDRX CoAP field node](../chapters/02-nb-iot-psm-edrx-coap-field-node.md)
and [Cat-M MQTT node with GNSS stamp](../chapters/03-cat-m-mqtt-node-with-gnss-stamp.md),
written on **Friday 16 October 2026**. They are in one record because they
were written in one sitting, on purpose, and that decision is most of what
this entry is about.

## Why together

The three earlier programs produced their shared code the same way. P18
needed what P04 already had, so the sequence accounting moved. P06 needed
what P18 already had, so the line reader moved. Both moves found a defect on
the way, which is an argument for the pattern rather than against it.

Both moves also happened after the fact. The code was written for one lab,
found to fit a second, and reshaped. That is the right order when the second
lab is a surprise. P02 and P03 were not a surprise: they are the only two
labs in the volume that drive a radio by typing at it, and anyone who has read
both chapters knows before writing a line that they want the same thing.

So this one was shaped by two sets of requirements at once, and it is worth
saying out loud that this is the exception rather than a change of practice.
The argument for waiting is that a library written for one user is a guess
about the second. The argument for not waiting here is that the second user
was already specified, in a chapter, in the same volume, and reading it took
ten minutes.

## What both chapters had, and what was wrong with it

Each printed a host loop of the same shape:

```python
def at(cmd, wait=1.0):
    ser.write((cmd + "\r\n").encode())
    time.sleep(wait)
    return ser.read(ser.in_waiting or 1).decode(errors="ignore")
```

That works on a bench and fails in a field, and the failure is nasty because
it is not a crash. It does not wait for the module to finish. It waits for a
number somebody guessed. A reply that takes longer than the guess is read as
the next command's reply, and from that moment every answer in the session
belongs to the question before it. The symptom is a log in which everything
looks almost right.

`lib/atchat.c` waits for a final line instead: `OK`, `ERROR`, a `+CME` or
`+CMS` error, or the prompt a module gives before a payload. A deadline bounds
the wait, and a deadline that expires is a timeout counted separately from a
refusal, because a module that is not listening and a module that declined
are different faults with different fixes.

## The transcript, which turned out to be the useful part

The engine reads a recorded conversation as readily as a serial port. That
began as a way to test with no HAT seated and became the more interesting
half, because of one decision: **each command the program sends is checked
against the one the recording expects.** A command in the wrong order is an
error, not a silent pass.

That makes a replay a test of the order of the conversation. P03's entire
claim is an ordering, that the GNSS receiver is powered down before the radio
transmits, and a transcript replay is that claim made executable with no
antenna in the room.

It also closes a loop that was not planned. A session against a real module
can be logged, the log is written in the transcript format, and the log can be
replayed afterwards with nothing attached. Both suites assert that round trip.

## P02: the arithmetic nobody does by hand

`AT+CPSMS=1,,"00100011","00000101"` is in the chapter, and what those two
bitmaps mean is not. Both are three bits of unit and five bits of value, and
**the two unit tables are different tables**: the periodic update timer is
GPRS Timer 3 of 3GPP TS 24.008 section 10.5.7.4a, the active time is GPRS
Timer of section 10.5.7.3. So they are three hours and ten seconds. Read with
the other table the first would be fifty minutes, and nothing on the glass
distinguishes those two readings.

The tables here are read from the specification. Nothing on this bench has
confirmed them against a network, and the chapter now says so where it prints
them.

Two further things fell out of having the numbers. The duty cycle becomes
arithmetic that can be checked before the bench run rather than discovered
during it: ten minutes and ten seconds is six datagrams an hour and about a
minute of the hour reachable. And the failure the chapter warns about in prose
becomes a comparison the program can refuse on, when the send period sits
inside the active window and the radio never reaches power saving at all.

**What the readback is not.** `AT+CPSMS?` returning the octets it was given
says the module accepted the request. The grant comes from the network and is
a different thing. The session prints that distinction in words rather than
printing a match and leaving a reader to draw the wrong conclusion.

## P03: a rule in two places, because one of them is not enough

Everything that transmits goes through one function, and that function
refuses while the receiver is powered. It does not log a warning and send the
command anyway. That makes the rule true of this program.

It is not enough, and noticing why is the useful part. The enforcement
protects one program. The chapter tells a reader to start in `minicom`, by
hand, and a hand-typed session has no such function in it. What it leaves
behind is a transcript.

So `p03 audit` asks the same question of a recording: was the radio asked to
transmit while the receiver was still on. It works on any transcript,
including ones this program could not have produced, and the `gnss-left-on`
scene exists so the audit has a known positive to find.

## A guard that could not be reached

Writing the suite found that the ordering guard is unreachable through the
public interface. Every path to a transmit powers the receiver down first, so
no sequence of public calls can make the guard fire.

That is the design working. It is also how a guard quietly stops working: a
check nothing can reach is a check nothing tests, and the next edit that
moves the power-down can remove the guarantee without failing anything.

The function is therefore declared in the header rather than kept private,
with the reason written beside it, and the suite calls it directly with the
receiver marked powered. The assertion that matters is not that it returns an
error. It is that **nothing was sent**: the transcript has not moved, which is
shown by the next command matching the recording's first line. A refusal that
still sent the command would be a log line pretending to be a rule.

## Found while compiling the chapters: seven titles cut in half

Both chapters failed `build.py --check` for a reason that had nothing to do
with this work. `main.tex` defined its note and rule boxes with `title=#1`,
unbraced, so a title containing a comma was split into two keys and everything
after the comma was dropped with a pgfkeys error.

Seven box titles in the volume contain a comma, including one written earlier
the same day. The published Markdown is unaffected, because it does not go
through LaTeX, so this only ever damaged the PDF and the HTML, which are local
to the authoring machine. Braced, and all seven chapters compile clean.

Worth keeping for the shape of it. The defect was old, it was in the one file
every chapter includes, and it was found by compiling a chapter that had just
been edited for an unrelated reason. Nothing in the repository was running
`build.py --check` over the sections, and the regeneration gate cannot see it,
because the Markdown that gate compares is produced by a different path.

## What is only a claim, as of Friday 16 October 2026
