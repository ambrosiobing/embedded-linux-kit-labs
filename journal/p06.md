# P06: a rule two chapters had written in prose, and the first program here that can be wrong in memory

The lab is [8x8 ToF occupancy kiosk](../chapters/06-8x8-tof-occupancy-kiosk.md),
written on **Friday 16 October 2026**, the third host side in this volume and
the first that writes into memory somebody else owns.

## Why this lab was third

The shape was different from the two that existed. P04 reads blocks and
transforms them, P18 reads sequence numbers and counts what is missing. Both
produce a number. This one produces a picture, through a mapping whose size is
decided by the kernel, which is a class of mistake neither of the others could
make.

## What `lib/` turned out to be for

When P18 was written the shared half was the sequence accounting, and the note
at the time said a library should hold what more than one lab turns out to
need rather than what was guessed at in advance. P06 has no sequence numbers
at all, so that file is of no use to it. What it needed was the other half of
P18's reading: the line reader.

That is worth recording because the two labs want it for different reasons
that turn out to be the same reason.

P18 refuses an over-long line because the remainder of a split line begins
with digits and arrives as a sample nobody sent. P06 refuses one because a
partial frame painted on the glass looks like a real reading and is not. Both
chapters already said so, in prose, in their pitfalls, before either program
existed. Prose does not run. The rule is now one function that both labs call
and that the suites of both labs test.

`lib/` now holds two files, and neither of them was written as a library. Both
were lifted out of a working program at the moment a second one needed them,
which is the only way either of them could have been the right shape.

## The three things the parser refuses, and why the count is four

The contract is sixty-five comma-separated fields, the first the literal `Z`.
A line that is not that is dropped, and the drop is counted under one of four
reasons rather than one: not a `Z` line, the wrong field count, a field that
is not an integer, and a distance no sensor in this kit can report.

Four counters rather than one is not tidiness. At a bench where everything is
being dropped, the reason is the diagnosis. Every line failing on the field
count means the firmware print is truncated. Every line failing on `Z` means
the recorder is pointed at the ST-LINK node rather than the sensor's, which
the chapter already warns is silent rather than an error. One counter would
have made those two look the same.

## The zero that is not a distance

A zone reporting zero millimetres is the sensor saying it found no target
there. Treating it as a distance makes an empty room read as something
touching the glass, which is wrong in the most alarming direction, so a zero
takes no part in the nearest-target answer and is never an occupied zone.

This is written down in three places on purpose: the header, the function that
computes it, and the chapter. It is the kind of detail that looks like an
implementation choice and is actually the difference between a kiosk that
works and a kiosk that reports someone standing in it all night.

## Refusing to produce a threshold

The chapter's instruction is "measure the threshold, do not guess it". A
program can only hold anyone to that by refusing to produce one from a
measurement that does not deserve the name, so `baseline` has two refusals:
fewer than ten frames, and a wall whose own frames disagree by more than the
20 mm the acceptance test allows.

The second one is the interesting refusal, because it catches the mistake
nobody notices. A baseline taken while something is moving in the field of
view produces a number, and the number looks exactly like a good one. The
spread is what separates them, and the spread is already in the acceptance
test for a different purpose.

The book also carries the placement as free text, for the same reason the
sibling lab's carries the mounting: the wall distance is a property of where
the sensor sits, and a threshold copied to the next bench, where the wall is
somewhere else, is a number pretending to be a measurement.

## The part that can be wrong in memory

The painter writes into an `mmap` of a device whose geometry belongs to the
kernel. Three decisions follow, and the last one is the test.

The geometry is read from the two text files the kernel already publishes,
`virtual_size` and `bits_per_pixel`, rather than through an `ioctl`. A reader
at the bench can `cat` the same two files and see exactly the numbers the
program is using, and the chapter's step prints them for that reason. It also
means no Linux-only header, and it means the suite can point the same code at
a directory it wrote itself.

Sixteen and thirty-two bits per pixel are painted and everything else is
refused by name. A display this program does not understand gets no pattern
written to it on the chance that it might look right.

Every rectangle is clipped, and the test for that is the one piece of this
suite that could not have been written in any other language the volume has
used. The glass is a file, longer than the geometry by 256 bytes filled with a
known value, mapped through the same path a framebuffer takes. The painter
runs. Then every byte past the end of the geometry is read back and must be
unchanged. Because `mmap` maps whole pages and the file is longer than the
mapping, a write a few bytes past the end would land in those guard bytes and
be visible in the file, so the check has teeth rather than relying on a
crash that may not come.

## The claim this lab makes, stated as a count

Nothing is painted that was not parsed. The paint happens inside the parse
loop and nowhere else, and there is no other call to the painter in the
program.

That is assertable rather than describable, which is the point. A stream of
twelve lines with five bad ones in it parses seven frames and writes the glass
exactly seven times. A stream whose only line is from the wrong talker leaves
the glass byte for byte as it was made. Both are in the suite, and the
workflow checks the same thing from the command line.

## What is only a claim, as of Friday 16 October 2026

**None of this has been compiled.** The authoring laptop has no compiler it may
use. `STATUS.md` leaves P06 at **written** with a row saying the state moves to
**checked** on the first green run and not before.

And one thing will stay a claim after that. Zone 0 is painted at the top left
and the zones run row by row, which is a convention this program fixes rather
than something read off the sensor. Nothing in a suite can confirm it. It takes
a hand in a known corner, and if it is wrong the fix belongs either in the
firmware's print order or in one loop here, and not in both at once.
